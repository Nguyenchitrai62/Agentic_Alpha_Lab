# BOT soak (bot_soak2): 24h accelerated replay through the fake Bybit V5

Rerun of bot_soak at reduced scope (24h, not 72h) so it finishes in < 90 min.
Harness: `tests/soak_bot.py`, mini version: `tests/test_bot_soak_smoke.py`
(2h, pytest). Fake exchange: `tests/mock_bybit_v5.py` (unchanged, reused).
No `bot/` code was edited; all findings below are reports with `file:line`.

  all five majors from `data/raw/majors_intraday_20260924` + `btc_intraday_20260924`).

  to replay closes each hour (offline; stated in the result JSON).
- Carry: `--carry-f 0.25` was ON, but there is no dated-futures/spot quote

  `_carry_cycle` sync/decide/guard runs every cycle, places nothing,

- Wall time: ~51 min (4320 cycles x mean 706 ms), wrapped in

## Bugs (bot/ NOT edited; file:line only)

- **B3 (root-caused, harness + bot): `ZeroDivisionError: float division by
  zero`, 264x, cycles 4007–4318 (from ~22:15, i.e. once XRP trailing sigma
  pegs at the 0.25 cap).** Chain: `tests/soak_bot.py` `make_plan`
  (`lv = bar_open * (1 - rung * sig)`) emits `buy_limit = 0` for rung 4.0
  whenever `sig` hits the `trailing_sigma` 0.25 cap
  (`tests/soak_bot.py:trailing_sigma` cap, `DIP_RUNGS` includes 4.0;
  final plan still shows 4 zero-limit XRP dips). The bot then divides by
  `lv` with no guard in `bot/mirror.py:479`
  (`frac * equity / lv * ...`), which raises inside `desired()` and
  propagates out of `Runner.cycle` (no try around `desired`), killing the
  cycle — the harness records `cycle_exception`, a live bot would skip
  protection for that cycle. Fix ownership: harness must clamp
  `buy_limit` to a positive tick (test-only), AND the leader should decide
  whether `mirror.desired` needs a `lv <= 0 → skip rung` guard (a real
  engine should never emit `buy_limit = 0`, but a crash-out-of-cycle is
  the worst possible response). Same family: 12x `170136: Abnormal order
  price` on `place` 23:00–23:04 (dip TP = `lv * 1.008 = 0`).
- **B1 (needs leader triage): book protection gaps, 5627 events.**
  Consistent with the known orphan-2nd-piece bug (`bot/mirror.py:301`,
  `next(...)` manages only the first book piece per (phase, symbol), so a
  side-flip that fills a second entry leaves the other without stop/TP;
  see the smoke-test docstring), but NOT proven for this run — the soak
  keeps no historical ledgers, and at end-state no sub-book holds >1 open
  piece (all resolved via divergence closes). To prove it, log
  (phase, symbol, open-piece-count) on each protection gap.
- **B2 (needs leader decision, real-money relevant): dip dust rests
  unprotected.** When a filled rung's TP/stop fall below the $5 minimum
  (high-sigma tiny `lv`, e.g. SOL rung 3.0/4.0 dust), `to_exchange`
  (`bot/run.py:130`) returns None (`skipped_below_minimum`, 9x) or the mock
  rejects (`170136`), and the piece sits open with no native protection
  (3864 events; 11 such pieces still open at end). Question for the
  leader: should the bot market-close dust it cannot protect, or is
  holding it acceptable? Either way the invariant should exempt nothing —
  the current gap is real.
- Non-bug note: 59380 `risk_reject` ops are the guard working as designed
  (dip qty explodes as `lv → 0`; per-coin/total/dip caps blocked them, and
  the dip-gross invariant held at 0 violations).
