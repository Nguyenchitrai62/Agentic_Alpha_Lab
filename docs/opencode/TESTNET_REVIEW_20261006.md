## 3. Rate-limit budget per runner per minute vs Bybit limits

What the repo itself says about limits: the ONLY numeric/code-level handling is `10006 = IP rate limit: back off and retry (public market data only)` with up to 4 attempts and `1.5*(attempt+1)` s sleeps, and **only inside `public()`** (`bot/bybit_v5.py:242-248`). Signed `get()`/`post()` raise immediately with no retry (`bot/bybit_v5.py:257-263`, `_check` `bot/bybit_v5.py:234-239`). Health counts `10006`/`rate limit` notes as warnings (`scripts/bot_health.py:226-227`, `:230`, `:234`); the runbook treats them as "wait, reduce frequency" (`docs/BOT_RUNBOOK_VI.md:89`); paper already showed `15x 10006` in one morning window (`docs/DEPLOYMENT_PLAN_VI.md:144`). **No Bybit limit table (requests/s or per-endpoint quotas) is stated anywhere in the reviewed files**, so the comparison below is budget-vs-handling, not budget-vs-quota — do not invent external quota numbers for a go/no-go.

Counted per `cycle()` in testnet/live with the recommended flags (interval 20 s → 3 cycles/min, `bot/run.py:565`):

- Normal cycle, signed (3/cycle → **9/min**): `equity_usdt` = 1× `GET /v5/account/wallet-balance` (`bot/run.py:405` → `bot/bybit_v5.py:303-305`); `sync_fills` = 1× `GET /v5/execution/list` (`bot/run.py:406` → `bot/bybit_v5.py:310-311`, windowed from `last_exec_ms` `bot/run.py:139-171`); `have` = 1× `GET /v5/order/realtime` (`bot/run.py:458` → `bot/bybit_v5.py:307-308`).
- Normal cycle, public (10/cycle + rare bear pages → **~30/min**): `last5()` = 5× `GET /v5/market/kline interval=5 limit=2` every cycle, uncached (`bot/run.py:183-189`, called `bot/run.py:415`); `last_close_1m()` = up to 5× `GET ... interval=1 limit=2` per cycle through `cached_call` TTL 20 s (`bot/run.py:221-248` → `bot/bybit_v5.py:143-153`, TTL `bot/bybit_v5.py:29`) — with a single runner TTL≈interval means mostly misses, so budget the full 5; `bear_now()` = 0 most cycles, 2× `GET ... interval=240 limit=1000` paged (`bot/bybit_v5.py:279-300`) once per 10 min when `--bear-book` (`bot/run.py:250-278`, `bot/run.py:435`) → amortised ~0.07/cycle.
- Normal-cycle total ≈ **13 req/cycle → ~39 req/min/runner** before any order action; order actions (`place`/`amend`/`cancel` via `send`, `bot/run.py:130-137`) add a handful in quiet markets (few amends/cancels from `diff`, `bot/mirror.py:695-715`).
- Crash / bar-end minute (exits + re-protection in the same cycle): each market exit is 1× `POST /v5/order/create` (`bot/run.py:415-434`); time exits can fire for ALL open dip pieces in one cycle (`bot/mirror.py:675-692`); each fresh fill then needs its stop+TP placed on the next cycle (`bot/mirror.py:361-366`, `:383-386`); failed stops retry next cycle and after >2 cycles an extra `unprotected_close` market order fires (`bot/run.py:498-537`); plan-gone pieces add `plan_closed_divergence` markets after grace (`bot/mirror.py:689-691`). Realistic burst: tens of POSTs in one cycle (e.g. 20 open dips → 20 market exits + subsequent 40 stop/TP places), i.e. **~60–150 signed POSTs/min in the worst minute on top of the ~39 base** — bounded by open-piece count, not by a client-side throttle (there is none for signed calls).
- Paper mode is heavier on public reads (extra 5× `GET ... interval=1 limit=1000` per `step()`, `bot/paper.py:152-165` incl. the kline call `bot/paper.py:159`), which explains the paper-side 10006 cluster above; testnet does not call `step()`.
- Mitigations already in code: shared on-disk kline cache across runners on one machine (`bot/bybit_v5.py:24-30`, `:96-153`, `:156-217`), 1m-close sharing (`bot/run.py:238-239`), 4h-open sharing with 10-min memo (`bot/run.py:263-265`, `:255-256`), `seen_exec` cap 500 (`bot/run.py:150`, `:171`), skip-log dedup per 4h bar with 2000-key bound (`bot/run.py:200-219`), cycle kept alive on exception (`bot/run.py:584-588`).

Assessment: the quiet budget (~39/min) is small and unlikely to trip IP limits alone, but (a) two runners (A+B) on one IP roughly double public reads unless the shared cache hits (`bot/bybit_v5.py:143-153`); (b) signed bursts have no throttle and no retry, so a crash minute can produce a run of `op=error` lines that are retried only next cycle (`bot/run.py:130-137`); (c) only public GETs back off — if testnet 10006s on signed calls, the bot logs and moves on, leaving the intended order for the next 20-s cycle. None of this is a no-go alone, but the first testnet run must watch `rate_limit` in `bot_health.py` output and keep A/B runners from sharing one tag/dir.

## 5. `bot/risk_guard.py` is NOT wired into live — exact call site proposal

- Status: pure, no I/O, `check(orders, positions, equity, prices, limits) → (allowed, rejections)` (`bot/risk_guard.py:1-7`, `:199-215`); never blocks reduce-only exits/protection (`bot/risk_guard.py:259-264`, `:210-214`); rejects `symbol_not_allowed / market_not_reduce_only / fat_finger / single_order_too_big / per_coin_cap / total_cap / dip_cap / bad_order` (`bot/risk_guard.py:213-214`, `:265-305`); defaults `per_coin 2.5 / dip 2.0 / total 4.0 / single 1.0 × equity, fat 15%` (`bot/risk_guard.py:15-22`); thoroughly unit-tested (`tests/test_bot_risk_guard.py:23-140`, 15 tests). **Nothing imports it**: `bot/run.py:23-25` imports only `mirror`, `bybit_v5`, `paper` — zero references to `risk_guard` in `bot/run.py`, `bot/mirror.py`, `bot/bybit_v5.py`.
- Proposed exact call site (testnet AND live, default ON, no new flags needed for the first testnet): in `Runner.cycle()`, **after** `want = mirror.desired(...)` + stale/plan_error trimming and **before** rounding/`diff`, i.e. between `bot/run.py:443` (`want = ...`) and `bot/run.py:458-469` (`have_before` → `rounded` → `diff`). Concretely, insert after the `if stale:` block (`bot/run.py:455-457`):
  ```python
  # PRE-TRADE GUARD (testnet review 2026-10-06): filter `want` before anything is rounded/sent.
  # prices = last CLOSED 1m closes (lc, bot/run.py:436) falling back to plan/last5 marks; equity = exchange equity (bot/run.py:405).
  # check() never blocks reduce-only exits/protection (bot/risk_guard.py:259-264), so stops/TPs/market exits always pass.
  allowed, rejected = risk_guard.check(want, self.state["ledger"], equity, prices)
  for r in rejected:
      self.log(dict(op="risk_reject", link=r.get("link"), symbol=r.get("symbol"), reason=r.get("reason")))
  want = {k: o for k, o in want.items() if o in allowed}  # or by link set
  ```
  Prices input: reuse `lc = self.last_close_1m()` (`bot/run.py:436`) merged with `coin_px`/plan marks used by bear-trim (`bot/mirror.py:601-609`); missing price → guard treats market-shaped orders as reject and caps as 0 (`bot/risk_guard.py:222-236`), which is fail-closed and correct for entries. Log reason `risk_reject` so `bot_health.py` error/reject accounting (`scripts/bot_health.py:208-234`) can surface it. Do NOT place the guard inside `mirror.desired()` (pure plan logic, tested bit-for-bit in `tests/test_bot_mirror.py`) and do NOT place it after `to_exchange()` (below-minimum skip, `bot/run.py:64-83`, must keep its own `skipped_below_minimum` signal distinct from risk rejects).
- Why here and not elsewhere: this is the single choke point every order kind (entry/add/reduce/TP/stop/bear-trim/dip-bid) passes through in both the normal path (`bot/run.py:439-469`) and — with a second identical insert — the no-cached-plan ledger-only path (`bot/run.py:360-374`), while market-exit payloads built earlier in the cycle (`bot/run.py:415-434`) are reduce-only and would pass through untouched anyway.
