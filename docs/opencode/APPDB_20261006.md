# app.db retention (measured 2026-10-06 on a read-only copy, live file never written)

1. Size 179,052,544 B (~170.8 MB, 43,714 x 4 KiB pages, ~zero freelist): bulk is STATIC frozen replays, not daily growth.
2. Per-table (fresh-DB measure, rows / bytes-per-row): run_books 877k / 86 B = 75.9 MB; trades 313k / 136 B = 42.5 MB; runs 175k / 102 B = 17.8 MB.
3. candles 217k / 65 B = 14.2 MB; orders 71k / 189 B = 13.4 MB; equity 186k / 28 B = 5.3 MB; jobs 985 / 865 B = 0.85 MB; kv 75 rows = 0.35 MB.
4. runs = 16x tm_* + walkforward x 10,944 bars each + ~300 live/paper rows; run_books/trades/orders/equity likewise replay-dominated.
5. Largest columns: kv trade_plan_* JSON (v376 62 KB); runs.payload live-only (~8.8 KB avg); jobs.message (<= 3.8 KB); trades.extra (<= 113 B).
6. Written each cycle/refresh: jobs (1 row/job via run_job), candles (upsert <= 155 rows/day), kv OVERWRITES (trade_plan_*, plan_status_*, data_check, input_check).
7. store_paper rewrites paper_* runs/books/trades/orders (net ~0 rows); auth writes sessions/tokens on login only; tm_*/walkforward/candles/kv-users never pruned.
8. Steady-state net growth ~20-50 KB/day (candles ~10 KB + jobs ~10-25 KB; 10-02 failure storm wrote 771 jobs ~= 0.6 MB); the ~19 MB/day in DISK_GROWTH was the backfill window.
9. Retention is OPT-IN, never scheduled: `python -m backend.maintenance --days 90` (dry-run default), `--apply` deletes, `--vacuum` reclaims; admin may call `prune_old_rows()` instead.
10. Prunes ONLY jobs (started_at) + live/paper_* runs family + paper_* orders/trades older than N days; NULL timestamps kept; tm_*/walkforward/forward/users/sessions/kv/candles/equity excluded in SQL.
11. Tested on a synthetic sqlite DB (tests/test_appdb_retention.py, 3 tests pass): dry-run is read-only; apply keeps frozen replays, identity, kv, candles.
12. Dry-run on the real copy with --days 90: 0 rows in every table (all ops rows are < 90 days old) -> expected size after pruning = 179,052,544 B, unchanged; it caps future jobs at ~30/day x 90 d ~= 2.3 MB.
